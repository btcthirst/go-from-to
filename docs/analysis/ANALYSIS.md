# Аналіз Проєкту: Excel/ODS Parser (go-from-to)

> Дата аналізу: 2026-02-20  
> Мова реалізації: Go 1.22  
> Ліцензія: MIT

---

## 1. Загальний опис

Проєкт є десктопним застосунком для обробки фінансових документів — файлів нарахувань (ODS) та банківських виписок (XLSX). Основна мета — автоматично знайти збіги між рахунками контрагентів у виписці та особистими рахунками мешканців у файлі нарахувань, замінити номери рахунків на ПІБ і зберегти результат у зведеному файлі.

Інтерфейс побудований на фреймворку **Fyne v2**, що забезпечує кросплатформений GUI з діалогами вибору файлів, табличним відображенням даних і асинхронною обробкою.

## 2. Архітектура проєкту

```
go-from-to/
├── cmd/
│   ├── app/main.go       — точка входу, запускає UI
│   ├── debug/main.go     — утиліта аналізу структури ODS (unidoc)
│   └── check/main.go     — утиліта перевірки ODS через ZIP/XML
├── internal/
│   ├── app/app.go        — бізнес-логіка обробки файлів
│   ├── excel/
│   │   ├── reader/
│   │   │   ├── reader.go     — читання XLSX виписок та нарахувань
│   │   │   └── ods_reader.go — власний парсер ODS (ZIP+XML)
│   │   └── writer/
│   │       ├── writer.go     — запис у XLSX
│   │       └── ods_writer.go — запис у ODS
│   ├── model/models.go   — структури даних
│   └── ui/ui.go          — Fyne UI-менеджер
└── docs/                 — документація змін (UI Guide, Quick Start тощо)
```

Архітектура дотримується принципу поділу відповідальностей: окремі пакети для читання, запису, моделей, бізнес-логіки та UI.

## 3. Ключові компоненти

### 3.1 Моделі даних (`internal/model/models.go`)

| Структура | Призначення |
|-----------|------------|
| `AccrualRecord` | ПІБ + особистий рахунок мешканця з файлу нарахувань |
| `PaymentRecord` | Запис платежу з банківської виписки (дата, сума, контрагент, призначення) |
| `ResultRecord` | Зведений результат з заміненим ПІБ, прапором відрахування, призначенням |

### 3.2 Читання файлів (`internal/excel/reader/`)

- **ODS** — реалізований власний парсер на основі `archive/zip` + `encoding/xml`. Файл ODS розбирається як ZIP-архів, витягується `content.xml`, парситься потоково через `xml.Decoder`.
- **XLSX** — використовується бібліотека `github.com/xuri/excelize/v2`.
- Пошук рахунку у даних контрагента здійснюється функцією `FindAccountInCounterparty` — простий пошук підрядка (`strings.Contains`).

### 3.3 Запис результатів (`internal/excel/writer/`)

- **XLSX** — через `excelize`.
- **ODS** — власна реалізація генерації ZIP-архіву з `content.xml`, `manifest.xml`, `meta.xml`, `styles.xml`, `settings.xml`.

Формат виведення: таблиця з 12 колонками (`№п`, `Постачальник`, `Дата`, `Дт рах.311 Сума`, `Оборот по Дт`, `313`, `63`, `641`, `641.1`, `651`, `94`, `Оборот по Кт`).

### 3.4 Бізнес-логіка (`internal/app/app.go`)

- `Init()` — запуск з жорстко заданими іменами файлів (legacy-режим).
- `ProcessFiles(accrualFile, paymentFile, outputFile)` — повна обробка з явними шляхами.
- `ProcessPayments(accrualFile, paymentFile)` — повертає `[]ResultRecord` без запису (для UI).
- `GetAccruals(accrualFile)` — повертає лише нарахування (для попереднього перегляду).
- `processPayments(...)` — приватна функція, виконує заміну рахунків на ПІБ і класифікує відрахування за від'ємною сумою.

### 3.5 UI (`internal/ui/ui.go`)

- Побудований на **Fyne v2.7.2**.
- Три таби: **Нарахування**, **Платежі**, **Відрахування** — з окремими `widget.Table`.
- Асинхронна обробка через горутини + `fyne.Do()` для безпечних оновлень UI.
- Кнопка "Зберегти як..." активується лише після успішної обробки.
- Діалоги відкриття/збереження файлів — стандартні системні через `dialog.NewFileOpen` / `dialog.NewFileSave`.

## 5. Виявлені проблеми та слабкі місця

### 5.1 Критичні

| # | Проблема | Розташування |
|---|----------|-------------|
| 1 | **`log.Fatalf` у бізнес-логіці** — у функції `ProcessFiles` при помилці відбувається завершення всього процесу (`os.Exit`), що унеможливлює коректну обробку помилки у GUI. | `internal/app/app.go` |
| 2 | **Дублювання логіки** — `ProcessFiles` і `ProcessPayments` містять майже ідентичний код читання нарахувань і платежів. | `internal/app/app.go` |
| 3 | **Стан `UIManager` не захищений м'ютексом** — горутини пишуть у `um.accruals`, `um.results`, `um.hasResults` без синхронізації, хоча `fyne.Do` частково вирішує це для UI-оновлень. | `internal/ui/ui.go` |

### 5.2 Середньої критичності

| # | Проблема | Розташування |
|---|----------|-------------|
| 4 | **Жорстко задані імена файлів** у `Init()` — не придатно для переносного використання без GUI. | `internal/app/app.go` |
| 5 | **`FindAccountInCounterparty` — O(n) на кожен платіж** — проходить по всьому списку рахунків для кожного запису виписки. При великих файлах це може бути повільно. | `internal/excel/reader/reader.go` |
| 6 | **Масова відладкова інформація у `fmt.Printf` / `log.Printf`** — DEBUG-виводи залишені в продакшн-коді, що засмічує вивід. | `reader.go`, `ods_reader.go` |
| 7 | **Неповне використання `trimRow`** — функція оголошена, але ніде не використовується. | `internal/excel/reader/reader.go` |

### 5.3 Стилістичні / minor

| # | Проблема |
|---|----------|
| 8 | Відсутні юніт-тести для будь-якого пакету. |
| 9 | Документація (`README.md`) частково застаріла — описує структуру `summery.xlsx`, тоді як поточний формат виводу змінився. |
| 10 | `cmd/debug/main.go` залежить від `unidoc/unioffice`, але та сама функціональність реалізована вручну у `ods_reader.go`. |

## 6. Позитивні аспекти

- **Чистий поділ відповідальностей** — reader, writer, model, app, ui — чітко розмежовані.
- **Власний ODS-парсер** — не потребує C-бібліотек, повністю портативний.
- **Асинхронний UI** — обробка не блокує інтерфейс.
- **Підтримка двох форматів виводу** (XLSX та ODS) з автоматичним вибором за розширенням.
- **Класифікація відрахувань** — від'ємні суми виводяться окремо у вкладці "Відрахування".

## 7. Рекомендації щодо покращення

### Короткострокові (легкі)

1. **Видалити DEBUG-виводи** або замінити на структурований логер з рівнями (`log/slog` зі стандартної бібліотеки Go 1.21+).
2. **Видалити невикористану функцію `trimRow`** або задіяти її у читачі.
3. **Перенести `unidoc/unioffice` у `tools.go`** або видалити з `go.mod`, якщо `cmd/debug` не є частиною продакшн-збірки.
4. **Замінити `log.Fatalf` на повернення `error`** у `ProcessFiles`, щоб GUI міг показати діалог помилки.

### Середньострокові

5. **Усунути дублювання** — винести спільну логіку читання файлів з `ProcessFiles` та `ProcessPayments` у приватну допоміжну функцію.
6. **Оптимізувати `FindAccountInCounterparty`** — для великих файлів доцільно побудувати `map[string]string` (рахунок → ПІБ) одноразово і використовувати пряму перевірку.
7. **Додати базові юніт-тести** для `reader`, `writer` і `processPayments`.

### Довгострокові

8. **Конфігурація** — вивести назви колонок, номери рядків заголовків у конфігураційний файл (YAML/TOML), щоб підтримувати різні формати вхідних документів без перекомпіляції.
9. **Оновити README** відповідно до поточної структури виводу та GUI-режиму роботи.

## 8. Підсумок

Проєкт вирішує конкретну прикладну задачу і має зрозумілу структуру. Основні ризики пов'язані з відсутністю тестів, DEBUG-кодом у продакшн та некоректною обробкою помилок у контексті GUI. Архітектура в цілому здорова і добре розширювана. При усуненні зазначених проблем проєкт готовий до надійного щоденного використання.
